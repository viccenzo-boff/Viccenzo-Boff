# Registro de Decisões — Currículo Técnico Premium

> Artefato de memória permanente (`.specify/memory/`). Cada linha é uma decisão
> tomada e o **porquê** dela — o que alguém reverteria com boa intenção se não
> soubesse o motivo. Complementa a constituição: lá ficam os princípios que
> governam toda entrega; aqui, as escolhas concretas já feitas.
>
> **Regra de escrita:** decisão sem racional não entra. O `diff` já diz o quê; o
> que se perde entre sessões é a razão.
>
> **Origem:** migrado de `.specify/memory/decisions.md` na adoção do Spec Kit
> (2026-09-02), preservado na íntegra. Decisões novas de uma entrega nascem no
> `plan.md` dela e são **promovidas** para cá quando viram permanentes
> (constituição, Artigo V.1).

Texto corrigido para o que é verdade. Racional: o card cita o repositório público na linha de baixo — texto de vitrine vem acompanhado do material que permite desmenti-lo, então a afirmação tem que sobreviver a quem abrir o link. |

| Hero é a única seção centralizada | Resolve o vazio em telas largas; as demais seções permanecem alinhadas à esquerda. |
| Hero preenche uma dobra via `svh` do CSS (não JS lendo `screen.*`) | O usuário pediu "detectar a resolução para a página sempre se encaixar". Unidades de viewport do CSS (`svh`) **são** essa detecção — o navegador resolve para o viewport real da janela. Ler `screen.width/height` via JS mede a tela física (não a janela), quebra com zoom/split-screen/resize e causa layout shift; foi descartado. `svh` (não `dvh`/`lvh`) para estabilidade no mobile — sem reflow quando a barra de URL some. Mecânica: `architecture.md` §5.6. |
| Fundir Tecnologias + Competências e Metodologias + Comportamentais na macro-seção "Habilidades e Ferramentas" | Pedido do usuário (2026-07-14): melhorar a escaneabilidade reduzindo três cabeçalhos repetidos a um só `h2`, com três blocos rotulados por subtítulo `h3`. Regra de ouro: migração **verbatim** dos cards (classes, Framer/`view()` e HTML internos intactos → tile de ícone, número fantasma e barra de prova preservados). Os painéis flat de Engenharia ganham uma **bandeja `bg-muted`** interna para não perder o relevo que a antiga `<section>` `bg-muted` dava; os `id` históricos migram para os blocos (busca/deep-links preservados). Mecânica: `architecture.md` §5.7. |
| Bloco Stack Tecnológica 100% hard-tech | Otimização para ATS; metodologias (SDD/PERT) ficam no bloco de Engenharia e Metodologias e no card do projeto. |
| Itens conceituais permanecem em Bancos de Dados | "Modelagem relacional" e "Controle de concorrência" são competências reais e keywords de ATS; validado pelo usuário (fecha B5, incl. rótulo "Orquestração de LLM (Gemini 2.5 Flash)"). |
| Sem badge de idiomas no Hero | Preserva o Hero minimalista; idiomas vivem no bloco "Base Acadêmica e Idiomas" da macro-seção "Formação e Desenvolvimento" (fecha B2). |
| Fundir Formação Acadêmica e Idiomas + Monitorias Acadêmicas na macro-seção "Formação e Desenvolvimento" | Pedido do usuário (2026-07-14): agrupar a vida acadêmica numa macro-seção elegante, sem perder nenhum efeito visual/animação. Mesma receita da fusão "Habilidades e Ferramentas": um `h2` + três blocos com subtítulo `h3` discreto, migração **verbatim** dos cards/índice/coda (medidores de idioma, ponto de status, dot leaders, coda intactos). **Escudo** implementado por token (`.section-heading` + `bg-background`) e subtítulos como eyebrow **sem placa**, coerente com a decisão V2.20 (escudo por token, não `bg-zinc-50 dark:bg-zinc-950` literal — `CLAUDE.md` §3) e com a macro "Habilidades e Ferramentas" — a linha é confinada à margem direita e nunca passa atrás dos títulos alinhados à esquerda, logo o escudo só é necessário no `h2`. Terceiro bloco **Certificações e Cursos** fica estruturado e **vazio** (sem dados em `cvData`) até o usuário decidir populá-lo ou ocultá-lo. `id` históricos migrados para os blocos (busca/deep-links preservados). Mecânica: `architecture.md` §3.2/§5.7. |
| Ordem do PDF ≠ ordem da tela | O PDF segue ordem de recrutador (contatos → resumo → impacto → experiência → …). |
| Scroll Progress Line em fluxo do documento, **atrás do texto** e acima dos fundos | Direção dada pelo usuário na revisão da V2.1 (overlay fixo na viewport e sobre o texto foi rejeitado). Como as seções pintam fundos sólidos, a linha vive num sanduíche de z-index — fundo da seção → linha `z-0` → conteúdo `relative z-10` — percorrendo a página inteira e desenhada na altura do scroll. Mecanismo e invariante para seções novas: `architecture.md` §5.5. |
| Gradiente roxo→azul→vermelho na Scroll Progress Line | Única exceção deliberada à paleta monocromática zinc, pedida pelo usuário como assinatura visual. Expressa em tokens dedicados `--scroll-line-*` (light/dark) em `globals.css`; todo o restante do site permanece monocromático. |
| Todo bloco de conteúdo em fundo opaco (cards) | Revisão da V2.1 (feedback do usuário): mesmo atrás do texto, a linha vazava pelos vãos das letras e através de cartões só com borda (monitorias). Experiência, tecnologias, competências, comportamentais e formação ganharam `Card`s no padrão do Painel de Impacto; monitorias ganharam `bg-background`. A linha passa atrás dos blocos e só aparece nos vãos entre eles. |
| Scroll Progress Line ancorada ao DOM, com trilho direito nos títulos | Revisão da V2.2 (feedback do usuário com capturas): os nós em frações fixas do documento caíam em cima de títulos — em posições diferentes no mobile e no desktop — e o início "brotava" no meio da tela. Medição real confirmou invasão de até 13 títulos somando os 4 viewports e que só descer o início não resolveria. Agora as âncoras são medidas do DOM: a linha nasce fora da borda esquerda e passa cada faixa de título presa a um trilho à direita do texto (curva monotônica em y ⇒ impossível cruzar título), com verificação geométrica automatizada em 375/768/1280/1920px. |
| Scroll Progress Line com vínculo 1:1 — **sem física de perseguição** | Especificação final do usuário (2026-07-12): "se eu descer X% da tela, a linha deve preencher exatamente X% do caminho" — resolve a ambiguidade "caminhada A→B" vs. "linear atrelada ao scroll" que atravessou as V2.1–V2.4. A fração desenhada é função pura e determinística do scroll (linearizada pelo mapa y→fração para a ponta ficar na altura do usuário — o "X% do comprimento" literal faria a ponta fugir da tela, pois a tortuosidade varia por seção). Quatro versões com física (spring, perseguição limitada, exponencial, mola crítica) falharam pela mesma razão estrutural: qualquer dinâmica entre scroll e desenho ou atrasa (teleporte do traço inteiro) ou dispara (dardo por tick) — post-mortem completo em `docs/scroll-line-postmortem.md`. Não reintroduzir suavização (armadilha registrada em `architecture.md` §9). |
| Glow de hover/focus como interação principal, derivado de `--signature-accent` | Pedido do usuário (2026-07-13): "gostei muito dessa mecânica visual" (o hover que acende Tecnologias com a assinatura) e "quero padronizar isso como a interação principal". Solução: uma **fonte única** (`--signature-accent` = a via do gradiente da linha) + duas primitivas em `globals.css` (`.signature-hover` para superfícies, `.signature-hover-text` para texto) aplicadas a todo card/título/botão/ícone das seções — dose homeopática, só no `:hover`/`:focus-visible`, sem cor nova (segue a exceção cromática única da assinatura, PRD §6/§8). O repouso continua 100% monocromático → contraste/a11y intactos por construção. Mecânica em `architecture.md` §5.7. |
| Hero com camadas de profundidade reutilizando a assinatura | Pedido do usuário (2026-07-12): o minimalismo do Hero estava "simples até demais" para o primeiro impacto; solicitou sombreamento nas letras, movimento leve e complexidade visual sem quebrar a estética. Solução: auroras/sheen/separador usam **exclusivamente** os tokens `--scroll-line-*` já existentes — a assinatura cromática nasce difusa no Hero e se materializa como linha a partir do Painel de Impacto; nenhuma cor nova entra na paleta. Tudo CSS puro (server component preservado, zero JS), reduced-motion respeitado por construção (`architecture.md` §5.6). |
| Auditoria de UI (2026-07): títulos fortes + menos recursos de assinatura | Pedido do usuário após a auditoria orquestrada (Frente 4/impeccable, modo "auditar e só relatar", aprovando item a item). (1) `h2` de seção: eyebrow uppercase → título sentence-case forte (hierarquia/varredura + fim do tell de eyebrow). (2) Removidos três recursos de assinatura acumulados: gradiente metálico do nome/métricas (→ sólido; tell de gradient-text), numeração fantasma 01–05 da Engenharia (→ painéis planos; mantida nas Monitorias, que são um índice **real**), barra de prova das Comportamentais (→ borda cheia; ban de side-stripe). O glow de hover, o tick dos títulos e as hairlines **permanecem** — a assinatura vive neles. (3) Badges de skill longos quebram no mobile. Racional: o impeccable é calibrado para greenfield e o register de marca preserva identidade commitada, mas o usuário optou por reduzir o acúmulo de "recursos de designer" para uma leitura mais confiante. Mecânica: `architecture.md` §5.3/§5.6/§5.7/§9. |
| Scroll Progress Line confinada à margem direita + escudo por token (não `zinc-*` hardcoded) | Pedido do usuário (2026-07-14): a linha estava "cruzando e dificultando a leitura dos títulos". Solução **geométrica e escalável**: a curva inteira passa a viver numa faixa disjunta da coluna dos títulos (à direita, ≈76%–92% da largura) — não-cruzamento garantido **por construção**, sem depender só da monotonia em y. O "escudo visual" pedido foi implementado com **tokens semânticos** (`bg-background`/`bg-muted` casando com o fundo de cada seção), e **não** com o `bg-zinc-50 dark:bg-zinc-950` literal do pedido: (a) `zinc-*` hardcoded é proibido em `src/components/custom` (`CLAUDE.md` §3); (b) metade das seções é `bg-muted` — uma cor fixa pintaria uma **caixa visível** atrás de metade dos títulos, um bug pior que o corrigido. A placa por token some no fundo e só recorta a linha atrás do texto. Mecânica: `architecture.md` §5.5/§5.7. |
| `cv_base.md` como spec de entrada espelhando `cv.ts` | Pedido do usuário (2026-07-16). O `cv_base.md` nasceu como texto-fonte bruto do currículo, mas ficou defasado conforme `cvData` evoluiu (V1.8+ adicionou Projetos, Idiomas, Stack Tecnológica, Métricas e a evidência de oratória sem atualizar o `.md`). Em vez de aposentá-lo, o arquivo é promovido a **espelho legível + spec de entrada**: o usuário registra ali, em linguagem natural, qualquer mudança de currículo real (curso, emprego, projeto, idioma, skill, métrica) e o Claude propaga para `src/data/cv.ts` seguindo os padrões do projeto, mantendo os dois sincronizados. Racional: o usuário descreve **o fato** (o que aconteceu no mundo real), não a tarefa técnica — o Claude traduz a spec em código. Fluxo em `CLAUDE.md` §3. |
